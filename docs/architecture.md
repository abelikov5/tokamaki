# Архитектура

## Компоненты

```text
Браузер
   │ HTTP
   ▼
Nginx ──► Laravel/PHP-FPM ──► PostgreSQL
               │                 Redis (следующий этап)
               │ internal HTTP
               ▼
        Python/FastAPI ──────► S3/MinIO (следующий этап)
```

- **Laravel** владеет пользователями, тарифами, платежами, заданиями и правами доступа к результатам.
- **Python** является вычислительным сервисом без знаний о пользователях и оплате.
- **PostgreSQL** хранит метаданные и состояния, но не бинарные изображения.
- **S3/MinIO** будет хранить оригиналы и артефакты; в прототипе Python использует локальный volume.
- **Redis** предназначен для очереди, прогресса и блокировок; синхронному прототипу он пока не требуется.

## Текущий сценарий

1. Браузер отправляет изображение и настройки в Laravel.
2. Laravel валидирует запрос и создаёт `generations` со статусом `processing`.
3. Laravel передаёт multipart-запрос внутреннему FastAPI.
4. Python создаёт PNG, SVG, PDF, палитру и диагностику.
5. Laravel сохраняет метаданные и отдаёт браузеру результат с собственными URL скачивания.
6. Laravel проксирует скачивание, поэтому Python не публикуется наружу.

## Переход к очереди

Публичный контракт можно сохранить. Контроллер будет возвращать `202 Accepted`, Laravel Job отправит задачу в очередь, а интерфейс будет читать статус либо получать события через WebSocket. Python можно масштабировать независимо несколькими workers. Идемпотентность строится вокруг `generation_id`, повторный callback подписывается HMAC.

## Данные

Текущая таблица `generations` хранит настройки, статус, идентификатор результата, палитру, диагностику и ошибку. Следующими таблицами станут `generation_artifacts` для файлов и `credit_transactions` для неизменяемого журнала списаний/возвратов.
